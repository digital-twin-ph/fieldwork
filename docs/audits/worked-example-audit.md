# Worked-example audit: what the examples exercise, and what only they carry

_Created 2026-10-29 · Updated 2026-10-29_

Generated by `scripts/audit-worked-examples.mjs` from the example registry the application
itself uses, `widgets/evidence.json`, `widgets/examples.json` and `widgets/standardization.json`.
Never hand-edited.

Two questions, and they are not the same. **Utilization** asks which widgets a workflow reaches:
a lab check establishes that a widget is right, and appearing in a workflow is the only evidence
here that it is useful. **Reconstructability** asks whether someone holding only what this
project publishes could rebuild an example — which is where a bespoke component or a bespoke
asset shows up.

## 2 · Generation from scratch

The test the practitioner set on 2026-10-29: *"I should be able to download all the input data,
start from a blank canvas and recreate the example from scratch."* Three things have to hold.
No widget attached to the example, every input obtainable, every parameter reachable from its
own panel.

**A bespoke asset is a node that carries a payload and declares no source.** Every worked
example carries data or it would not open; the question is whether the node says where that
data came from, because a node that names its source can be rebuilt by fetching it and a node
that does not can be rebuilt only by copying this file.

### What this cannot establish

- **That a declared source resolves.** This reads whether `sourceInfo` or `provenance` is
  present, not whether the URL answers or the digest matches. `validate:examples` checks the
  pinned bundle's digests; nothing checks a shipped example's declared source.
- **That every parameter is reachable from its panel.** Only a rebuild can show that, and only
  one exists: `tests/recreate-from-scratch.browser.mjs` builds `south-london/ground` from an
  empty canvas and the published files. The other five South London workflows and all
  11 shipped examples are unproven on this point.
- **That a published input could be DERIVED in the application.** This is the sharpest limit on
  the rebuild test and it was found by the practitioner on 2026-10-29: *"The way we selected the
  Thames waterways polygons seem to be bespoke."* It is. `geo/thames-reaches.geojson` records its
  own method — OpenStreetMap water-area multipolygons *"partitioned where relations 308126 and
  318374 meet at Teddington Lock"*, then clipped to the study box — and no widget performs that.
  Two capability gaps put it out of reach: nothing selects or removes features from a polygon
  layer by their attributes, and nothing splits a polygon at a line, since no widget reads a
  LineString at all. So a rebuild from published inputs proves ONE link. The chain from a primary
  source to a published input is unproven, and for this layer it currently runs outside the
  application. An input whose provenance is recorded is not the same as an input a practitioner
  could produce.
- **That an unused widget should be retired.** D11 asks whether a residual function remains
  that nothing else performs. A widget may be unused because no example poses its problem yet,
  which is a gap in the examples rather than in the palette.

## 3 · Recommendations

Generated from the numbers above, so a recommendation cannot outlive the gap that produced it.
Each says what was measured and what closing it would mean. None says whether it is worth
doing: that is a decision with a cost, and this file measures.

**R1. Give the 11 data-carrying nodes a declared source.** 7 shipped examples hold 11 nodes that carry data and name no origin: `heat` (2), `coverage` (1), `snow-voronoi` (1), `snow-isochrone` (2), `sea-level` (2), `snow-extent` (1), `rulesets` (2). Closing it means either a `sourceInfo`/`provenance` block naming where the data came from, or a published file beside the example the way `geo/water-intakes.geojson` was written on 2026-10-29. Until then each is a payload a rebuild must copy rather than fetch.

**R2. Ask D11 of the 7 widgets no workflow reaches.** `buffer_point`, `deduplicate_points`, `fill_interior_gaps`, `measure_area`, `sample_raster`, `slr_threshold_comparison`, `summarize_combined_area`. Not a retirement list: D11 asks whether a residual function remains that nothing else performs, and a widget may be unreached because no example poses its problem. The answer is per widget and this audit does not have it.

**R3. Settle what a monolith and its decomposition owe each other.** Use propagates from a composition to its members and not from an equivalent monolith, so 4 widgets read as unreached while a workflow performs their work. It is a question about the admission criteria rather than about those widgets, and the count is deliberately left as it is until it is answered.

**R4. Give a second workflow to the widgets one example carries alone.** `south-london-1854` is the sole evidence for 11 widgets. Restructuring an example can take that evidence with it and nothing reports the loss. Closing it means a second workflow reaching those widgets, or recording the fragility as accepted.

**R5. Extend the from-scratch rebuild past one workflow.** `tests/recreate-from-scratch.browser.mjs` proves `south-london/ground` can be built from an empty canvas and published files. The other five South London workflows and all 11 shipped examples are unproven, and it is the only test that can show a parameter is reachable from its own panel.

**R6. Check that a declared source resolves, not only that it exists.** This audit reads whether `sourceInfo` or `provenance` is present. `validate:examples` verifies the pinned bundle's per-file digests; nothing verifies a shipped example's declared source, so a dead URL or a moved file reads as declared.

**R7. Resolve the 4 widgets attached to one example.** `old-naledi`: `facilities`, `facility_audit`; `snow-geoprivacy`: `comparison_map`; `sea-level`: `slr_site_assignment`. Each is already carried in `widgets/standardization.json` with the record that would remove it, and the exemption ceiling may fall and may never rise.
